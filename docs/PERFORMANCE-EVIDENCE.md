# Isolated sales-history query evidence

Generated by `StoreTest.syntheticQueryPlanUsesPrimaryIndex` on MySQL 8.4.8.

Dataset: 5,000 synthetic sale headers in `marketflow_test`; no business database records. Query is a deep-history page; its cursor identifies the midpoint.

```sql
SELECT * FROM sales WHERE id < 17719 ORDER BY id DESC LIMIT 51
```

EXPLAIN: key `PRIMARY`, access type `range`.

```text
-> Limit: 51 row(s)  (cost=500 rows=51) (actual time=0.0924..0.104 rows=51 loops=1)
    -> Filter: (sales.id < 17719)  (cost=500 rows=2500) (actual time=0.0914..0.101 rows=51 loops=1)
        -> Index range scan on sales using PRIMARY over (id < 17719) (reverse)  (cost=500 rows=2500) (actual time=0.0901..0.0963 rows=51 loops=1)

```

The page requests at most 51 rows: 50 displayed plus one look-ahead. Primary-key range access avoids scanning an increasingly deep OFFSET prefix.

This is one local synthetic query-plan measurement, not a production capacity benchmark. Server timings vary. It does not establish inventory scaling, connection-pool throughput, end-to-end latency, or concurrent-user capacity. The OFFSET above is only used to choose a test cursor, not by the application.
